# 2026-09-29

## WorkBuddy 模块"未识别"修复（Token Monitor）

用户反馈 WorkBuddy 页签"实际模型"列全部显示"未识别"。根因不是解析缺失，而是**共享预热器 bug**：

- `HistoricalUsageBatchWarmer.WarmDays` 用标量 `Add(timestamp,...)` 重载构建日桶，
  丢失 `ModelUsage/ServiceTierUsage`；而 `usage_events` 明细行带 model_id。
- 结果：`usage_days.model_usage_json = '{}'` + is_complete=1 → 永不重扫 → 日行永远"未识别"。
- Codex 不受影响（有自己的 warmer，用事件重载 `CreateBucketFromEvents`）。
- 受影响模块：Claude/ZCode/WorkBuddy/DSH/Kimi（全部共用该 warmer）。

### 修复（3 处）
1. `HistoricalUsageBatchWarmer.cs`：改用事件重载 `bucket.Add(item)`（保留模型归因）。
2. `UsageCacheStore.InitializeDatabase`：一次性迁移 `warmer-model-context-v1`，
   重置 events>0 且 model_usage_json 为空且明细带 model_id 的天 → 下次启动重预热恢复
   （明细事件已在库中，源日志删了也能恢复）。
3. `WorkBuddyUsageReader`：从 `providerData.rawUsage.completion_thinking_tokens`
   （回退 completion_tokens_details.reasoning_tokens）解析推理 token，"推理"列与 DSH 对齐；
   `WorkBuddyUsageEntry` 增加 Reasoning 字段并计入 CompletenessScore。

### 测试

  （Claude/ZCode/WorkBuddy/DSH/Kimi 五源，含二次预热不丢模型断言）；Kimi 加入 Warm switch。
- `WorkBuddyUsageReaderTests`：新增 `ReadTransientDetailRows_CarriesReasoningTokensFromRawUsage`。

  `message.usage`（input/cache_read/cache_write/output/total）。2026-07 与 09 格式一致。

### 关键坑：已存在的用户配置不会吸收改动后的默认值
- `PriceSettingsStore.Load → Normalize` 只在 `DisplayOrderVersion` 提升时 `MergeMissingDefaults`
  （仅补缺失条目，绝不覆盖已有条目）。所以新增/改价对用户已保存的
  `%LOCALAPPDATA%\CodexTokenMonitor\price-settings.json` 无效 —— Hy4 仍是 0。
- 解决：`Normalize` 中新增幂等 `FillPublishedRate`，只对"四项价格仍全为 0"（用户从未填过）
  的 Hy4 Preview 行写入官方价；非 0 即用户自定义，保留。Load 时若 json 变化会自动回写磁盘。
- 副作用/注意：**跑测试会落盘写用户真实配置**（`PriceSettingsStore.Current` 走真实路径），
  所以定价类测试失败时先查 `%LOCALAPPDATA%\CodexTokenMonitor\price-settings.json`，别只看代码默认值。
